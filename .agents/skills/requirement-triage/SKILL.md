# Requirement Triage

Hub-specific triage for org requirements. Full process:
[`docs/agents/requirement-fanout.md`](../../../docs/agents/requirement-fanout.md).
Labels match harness triage names.

## Labels

Exactly one **category** and one **state**:

| Kind | Labels |
| --- | --- |
| Category | `bug`, `enhancement` |
| State | `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` |

## Invocation

Natural language, e.g.:

- “Triage this requirement: …”
- “What’s needs attention on the hub?”
- “Move #N to ready-for-agent”
- “Scaffold a plan for …”

## Steps

1. **Orient** — Read `CONTEXT-MAP.md`; load only relevant `domains/*/CONTEXT.md`.
   Read [`org/links.yaml`](../../../org/links.yaml) when naming target repos.
2. **Gather** — If an issue/PR is named: `gh issue view` / `gh pr view` with
   comments. Parse prior triage notes. Check redundancy against catalogue +
   existing `plans/`.
3. **Recommend** — Propose category + state + target repos. Wait for maintainer
   direction unless the user already said “just do it”.
4. **Grill gaps** — One clarifying question at a time when acceptance or target
   repos are unclear → `needs-info` until answered.
5. **Apply outcome**
   - `ready-for-agent` — scaffold or update `plans/<NNN>-<slug>/PLAN.md`;
     ensure the hub issue has a per-repo checklist; post an agent brief
     (template below). Progress is tracked only on that issue.
   - `ready-for-human` — same brief structure; note why not agent-ready.
   - `wontfix` — short reason; no plan folder required.
   - `needs-triage` / `needs-info` — label only + questions.
6. **Hand off** — Tell root to run `product-lead` for plan ownership + issue
   checklist and `engineer-in-<role>` task breakdown. Do **not** implement
   product code. Do **not** create `PROGRESS.md`.

## Agent brief template

Post on the hub issue (disclaimer first line):

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one line

**Plan:** `plans/<NNN>-<slug>/PLAN.md`

**Target repos (fan-out order):**
1. `repo` — work package
2. `repo` — work package

**Desired behavior:** …
**Acceptance criteria:**
- [ ] …
**Out of scope:** …
**Verification:** per-repo commands from each product `AGENTS.md`
```

## Hard rules

- Do not edit `checkouts/` product code
- Do not push, open PRs, or close issues unless the user asks
- One PR per repo later — never invent a multi-repo PR
- Keep hub `AGENTS.md` free of long triage prose; update this skill/docs instead

## Remote writes

When the user allows: `gh issue create` / `gh issue edit` / `gh issue comment`
